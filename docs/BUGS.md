### Authenticated (account-owned) path
- [x] Login verified: session established, survives full page refresh (checked via Profil page showing "Innlogget som"/"Logg ut").
- [x] Authenticated tournament creation verified: `owner_user_id` correctly bound to the logged-in account, `retention_expires_at` null at creation (not subject to guest 7-day expiry).
- [x] Authenticated tournament finish verified: record correctly **kept** (not deleted, unlike guest tournaments), status "Avsluttet", finalization receipt recorded.
- [x] Bug found, fixed, and verified. A pre-existing trigger `set_tournament_lifecycle_dates` (from migration 20260828121000, predates this session) used `coalesce(new.retention_expires_at, ...)` when a tournament transitions to "Avsluttet", which silently overwrote `finalize_tournament`'s explicit `retention_expires_at = null` for account-owned tournaments with a 30-day expiry. No data-loss risk occurred — `cleanup_expired_tournaments` only deletes rows where `owner_user_id is null`, so the wrongly-set date was never acted on — but the stored value was factually wrong. Fixed by guarding the trigger on `owner_user_id is null` (guest-path logic unchanged); the one already-affected row was corrected. Regression-verified with a fresh authenticated tournament: created → started → finished → `retention_expires_at` correctly `null`.
- [x] Fixed and verified. A logged-in account owner could not actually run a tournament: `admin_set_result`, `admin_advance_round`, `admin_advance_cup`, `admin_match_action`, `admin_undo_match`, and `delete_tournament` were all granted `EXECUTE` to the `anon` Postgres role only, never `authenticated` — confirmed via `has_function_privilege(...)` and reproduced live (registering a result while logged in failed with a 403 / `permission denied for function admin_set_result`, Postgres error 42501). All prior authenticated tests that session force-finished immediately without registering a result, which is why this was missed until now. The client correctly surfaced the failure rather than lying about success (DB confirmed: revision unchanged, match still "active", no score saved) — no data corruption, but the authenticated result-registration/round-advancement/match-action/undo/delete path was completely non-functional. Predates the session it was found in. Fixed by granting these 6 functions to `authenticated` (developer ran the SQL in Supabase Dashboard), matching the already-correct `create_tournament`/`finalize_tournament` grants and the functions' own security model (they authorize by admin_token possession inside the function body, not by Postgres role, so this only closed an access gap, not a new security surface). Verified via `has_function_privilege` returning true for all 6 functions, then end-to-end via a full authenticated-owner Round Robin playthrough: registered Round 1's result, advanced to Round 2, registered its result, advanced to Round 3, registered its result, finalized the tournament — every step persisted to Supabase correctly (revisions 2→7, confirmed by direct DB query after each action).
- [x] Verified. Natural Round Robin completion (play every round to its own end rather than force-finishing) and full-tournament standings were previously untested — now run end-to-end on a 4-player/1-court tournament (3 rounds, 1 match each). Each "Start neste runde" click correctly advanced the round server-side once all of the active round's matches reached `state: "finished"`, and final standings were verified mathematically correct against the 3 registered results (points, wins, sets, and games all tallied exactly). One harmless data inconsistency found along the way: `admin_set_result_impl` updates a finished match's `state` field to `"finished"` but never touches its separate `status` field, which stays at whatever it was before (e.g. `"active"`). This does not currently break anything — both `admin_advance_round_impl` (server) and `canCompleteRound`/`roundProgress` (client, in `app/tournament-status.js`) key off `state`, not `status` — but the two fields drifting out of sync is fragile groundwork for a future bug if any code path is ever added that trusts `status` instead. Fixed and verified. `supabase/migrations/20260915040000_admin_set_result_status_sync.sql` (adds the missing `status` writes alongside every existing `state` write in `admin_set_result_impl`, no other behavior change) applied by the developer in Supabase Dashboard SQL Editor. Verified directly: created a throwaway test tournament with a match in `state: "playing"`/`status: "active"`, called `admin_set_result_impl` with a winning score, and confirmed the returned match now has `state: "finished"` **and** `status: "completed"` together (previously `status` would have stayed stuck at `"active"`). Test row cleaned up via `finalize_tournament` afterward.

## Bug completion rule

A bug is complete only when:

- [ ] Reproduced or clearly verified.
- [ ] Smallest safe fix implemented.
- [ ] Relevant behavior tested.
- [ ] Critical-path regression checked.
- [ ] Status updated.

Do not spend time producing long bug-analysis documents.
